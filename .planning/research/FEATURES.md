## Catalog: Every `gsd-sdk query` Subcommand in the GSD Command Surface

Legend (Class column):
- **STATE** — derives from STATE.md/ROADMAP.md/phases/todos/REQUIREMENTS — must bd-back
- **NARRATIVE** — reads narrative/free-form markdown — passthrough OK
- **CONFIG** — reads/computes config or init metadata, no bd involvement — passthrough OK
- **DERIVED** — composite handler that internally calls other state-bearing handlers; will be fixed transitively when its inputs are bd-backed
- **OVERRIDE** — already in `BEADS_OVERRIDES` (mutation, v0.1 covered)

`/gsd-execute-phase`, `/gsd-plan-phase`, and the autonomous workflow on
beads-managed projects today. Without bd-backing, the upstream handlers go
hunting for `phases/01-foo/01-01-PLAN.md` files that exist (regenerated by
`bd-export-roadmap.sh`) but were authored from beads, so disk-vs-bd drift will
silently corrupt routing.

## Sufficient Coverage Test (vs the user's named four)

The user named **four** target handlers: `roadmap.analyze`, `state-snapshot`,
`progress.bar`, `progress.json`.

That set is **NOT sufficient** to restore `/gsd-progress`,
`/gsd-resume-work`, `/gsd-execute-phase`, `/gsd-plan-phase`, and
`/gsd-insert-phase` on bd-managed projects.

**Specifically, the four miss these critical state-bearing reads** (each of
which a P1 workflow calls directly, NOT via `roadmap.analyze`):

1. **`state.json`** — `next.md:17` (gates `/gsd-next`); also internally consumed
   by `route.next-action`. Without bd-backing, `/gsd-next` reads stale/derived
   STATE.md and routes to wrong commands.
2. **`state.load`** — `do.md:29`, `ship.md:23,181`, `settings.md:16`. The
   `/gsd-do` command uses it as its primary state probe. Returns `state_raw`
   verbatim — must be regenerated from beads.
3. **`roadmap.get-phase`** — called from **at least 11 distinct workflows**
   including all `/gsd-discuss-phase`, `/gsd-plan-phase`, `/gsd-research-phase`,
   `/gsd-ai-integration-phase`, `/gsd-ui-phase`, `/gsd-verify-phase`,
   `/gsd-autonomous`. A bd-backed `roadmap.analyze` does **not** cover this —
   they are independent handlers. Without bd-backing this, anything that
   resolves a phase by number (`PHASE_INFO=$(gsd-sdk query roadmap.get-phase
   "${PHASE}")`) returns either wrong data or `{found:false}`.
4. **`find-phase`** — `next.md:86`, `audit-milestone.md:49`, `execute-phase.md:1153`.
   Drives the iterative "scan all prior phases for incomplete work" pass in
   `/gsd-next`. Returns `{ plans, summaries, incomplete_plans }` from disk
   listing. Without bd-backing, the disk listing post-regen is correct only if
   `bd-export-roadmap.sh` produced phase dirs that mirror bead state — fragile.
5. **`init.phase-op`**, **`init.execute-phase`**, **`init.plan-phase`**,
   **`init.verify-work`** — DERIVED handlers that **internally call**
   `findPhase` + `roadmapGetPhase`. They will be transitively fixed by
   bd-backing #3 and #4. But because they are the entry points to **17+
   workflows** (every phase-scoped command), this proves #3 and #4 are P1.
6. **`init.progress`** — `progress.md:15`, `milestone-summary.md:56`.
   **Independent of `roadmap.analyze`** — it does its own ROADMAP+disk scan and
   produces a different shape (`{ phases: [{directory, status,
   has_research}], current_phase, next_phase, paused_at, has_work_in_progress }`).
   Without bd-backing this directly, `/gsd-progress` and
   `/gsd-milestone-summary` will misroute even after `roadmap.analyze` is fixed.
7. **`init.todos`** — `add-todo.md:15`, `check-todos.md:15`. Reads
   `.planning/todos/pending/*.md`. For bd-managed projects, todos live as task
   beads with `gsd:todo` label. Without bd-backing, every new todo creates a
   pending file that lives outside the bead store — divergence guaranteed.
8. **`init.milestone-op`** — `audit-milestone.md:19`, `autonomous.md:51`. Reads
   ROADMAP for phase count + scans disk for completion. The autonomous workflow
   gates ENTIRELY on `all_phases_complete` from this handler.
9. **`phases.list`** — `audit-milestone.md:35`, `execute-plan.md:144`,
   `plan-milestone-gaps.md:68`. Disk listing of phase directories. Bd version
   reads `bd list -l gsd:phase`.
10. **`phase.next-decimal`** — `decimal-phase-calculation.md`, used by
    `/gsd-insert-phase` and `/gsd-add-backlog`. Computes next free `X.Y`
    decimal under base phase. Reads disk + ROADMAP. Without bd-backing,
    inserted phases collide with existing decimals.
11. **`phase-plan-index`** — `execute-phase.md:239,1078`. Wave/autonomous/
    files_modified for parallel plan execution.

**Conclusion: v0.2 must bd-back at minimum the 16 P1 handlers in the table
above** (the user's 4 + 12 more). That is the minimum to restore the four
broken commands listed in the milestone goal.

### Dependency Notes

- **`route.next-action` is fixed for free** once `state.json` + `roadmap.analyze` + `find-phase` are bd-backed. No separate handler needed.
- **`init.phase-op` / `init.execute-phase` / `init.plan-phase` / `init.verify-work` are fixed transitively** once `find-phase` + `roadmap.get-phase` are bd-backed. But the on-disk artifact path detection (`has_research`, `has_context`, `verification_path`) STILL reads disk, which is correct because narrative artifacts stay narrative.
- **`progress.bar` is fixed transitively** once `progress.json` is bd-backed.
- **`state.json` and `state.load` are independent** — both must be handled. `state.json` rebuilds from disk via `buildStateFrontmatter`; `state.load` returns raw STATE.md text. For bd-managed projects, regenerating STATE.md from beads via `bd-sync.sh` BEFORE the read is the cleanest path; otherwise both handlers need explicit bd shims.
- **`todo.match-phase` needs `init.todos` semantics** — its standalone todo enumeration must match the bd-backed `init.todos` view, otherwise scoring is computed against stale todo files.
- **`phase.next-decimal` is independent** — it reads BOTH `.planning/phases/` (decimal child dirs) AND ROADMAP.md (phase headings). Its bd version: `bd children <base-phase>` filtered by `inserted` label.

## Open Questions for Roadmap

1. **STATE.md regeneration strategy:** Does `state.load` return `state_raw` from a freshly-regenerated-by-`bd-sync.sh` STATE.md, or do we synthesize the text inside the handler? The former is simpler and consistent with how ROADMAP.md is handled. Confirm with PROJECT.md and v0.1 sync semantics.
2. **`init.manager` scope:** `init.manager` is large (~200 lines, multi-section recommendation logic) and primarily transitive. Should v0.2 explicitly test it, or treat as "transitively fixed" with no test coverage?
3. **State **mutation** handlers (state.update, state.patch, state.advance-plan, etc.):** Not in v0.1 BEADS_OVERRIDES. The hook layer at `~/.claude/settings.json` blocks STATE.md writes. But these handlers go through `gsd-sdk`, not direct file writes. Are they currently caught by the hooks at the SDK level, or do they slip through? Verify before v0.2 ship.
4. **PLAN.md frontmatter (`wave`, `autonomous`, `files_modified`, `must_haves`):** These drive `phase-plan-index`, `verify.artifacts`, `verify.key-links`. PLAN.md stays narrative per PROJECT.md non-goals. Do we keep frontmatter file-based even on bd-managed projects? If yes, then `phase-plan-index` becomes a partial bd-back (IDs from beads, frontmatter from disk).
