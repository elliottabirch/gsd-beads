## What this spike must answer

1. **Does `bd dep add A B` (default blocks) make `bd ready` correctly return A only after B closes?**
   - Setup: `bd add` two phase epics A and B. `bd dep add A B`. Both open → `bd ready` should return only B (A is blocked). Close B. `bd ready` should now return A.
   - Expected: ordered semantics work as advertised. If they don't, option (a) is dead.

2. **Does the `blocks` relation appear in `bd export --json`'s `dependencies[]` array with `type: 'blocks'`?**
   - Critical for the read handler — we need to query the graph from the JSON output, not via separate `bd deps` calls (REQ-QUAL-07 ≤2 spawn budget).
   - Expected: `bead.dependencies[]` contains `{type: 'blocks', depends_on_id: '<other-bead-id>'}`. If missing, option (a) needs a separate `bd deps` call per phase, breaking the budget.

3. **Does cascade-loop (`bd epic close-eligible`) interfere with blocks-type deps?**
   - The cascade-close logic operates on `parent-child` only (per spike findings). Confirm `blocks` edges don't cause unintended closures.
   - Expected: closing all of A's blockers does NOT auto-close A. A still requires explicit close. If cascade closes A on B-close, that breaks the model.

4. **Does `blocks` survive JSONL roundtrip (`bd init --from-jsonl`)?**
   - The seed.jsonl flow: `build-seed.sh` invokes bd, writes to JSONL, fixture restorer replays. If `blocks` edges don't roundtrip, the seeder needs a different storage convention.
   - Expected: edges restored byte-identically. Same shape on both sides of the roundtrip.

5. **Does the determinism test (`tests/shadow-tests/seed-determinism.test.sh`) still pass after seeding `blocks` edges?**
   - bd export ordering for `dependencies[]` must be stable across reseeds.

6. **(Optional) does `bd dep tree A` correctly visualize the chain when `blocks` is used?**
   - Useful for debugging; not blocking.

## Success criteria for spike → option (a) is valid

- All 5 questions above answer YES.
- One Phase 5.6 plan can be written with confidence using `bd dep add ... <child> <parent>` semantics.
- Read handler can extract via `bead.dependencies[]` filtered by `type === 'blocks'` in a single export call.

## Failure modes to watch for

- Cascade-close pulling in blocks-type edges → option (a) dead; pivot to option (b) `--type depends-on`.
- Roundtrip drops the `blocks` edges → seeder convention has to change; option (a) feasibility depends on workaround cost.
- `bd export --json` doesn't surface the `dependencies[]` array reliably for `blocks` (only for `parent-child`) → forces per-phase `bd deps` call → blows the spawn budget; option (a) becomes expensive.
